# README showcase — real engine output

Everything in this folder was generated by the actual Typodeck pipeline
(`planDeck` → `exportToPptx` → `validatePptx` via the `npm run deck` CLI).
Nothing here is hand-drawn.

## Engine output vs brand illustration

- `docs/showcase/` (this folder) = **engine output**: real CLI-produced PPTX
  files, their deck JSON, provenance receipts, and PNG rasterizations of the
  real PPTX bytes.
- `brand/` = **hand-made identity illustrations** (wordmark explorations, hero,
  social card). They show the visual identity, not engine output. Do not mix
  the two when captioning README images.

`unverified · illustrative` captions — visible in the dense PNG.

## Reproduce

From the repo root (Node >= 20.9, after `npm ci`):

```sh
npm run build -w @typodeck/core
npm run deck -- --idea-file docs/showcase/ideas/editorial.txt --system editorial \
  --purpose "Flagship roastery investment case" --out /tmp/repro-editorial.pptx
npm run deck -- --idea-file docs/showcase/ideas/swiss.txt --system swiss \
  --purpose "Tool showcase: Ledgerline" --out /tmp/repro-swiss.pptx
npm run deck -- --idea-file docs/showcase/ideas/expressive.txt --system expressive \
  --purpose "Festival launch: Fieldnotes Live" --out /tmp/repro-expressive.pptx
npm run deck -- --idea-file docs/showcase/ideas/dense-technical.txt --system swiss \
  --purpose "Architecture review: Meridian Edge 2.0" --out /tmp/repro-dense.pptx
```

Each run prints a receipt (`provider`, `claims`, `deck`, `validation: OK`).
The CLI exposes no `--seed` flag: layout seeds derive from a content hash, so
the same idea bytes deterministically reproduce the same deck JSON (verified:
re-run of the swiss deck produced byte-identical deck JSON, seed 420076315).
Deck JSON + provenance companions were emitted by re-running `planDeck` on the
same inputs and validating the CLI-produced PPTX against it.

## Editable-PPTX proof

Independent check over the shipped `.pptx` zips (same method as
`showcase/spot-check.py`): every block's full text appears in editable `<a:t>`
nodes, and zero forbidden elements (`p:pic`, `p:cxnSp`, `p:graphicFrame`,
`a:blip`, `p:contentPart`, `a:tbl`, `v:shape`, `a:gradFill`) exist:

- readme-editorial: slides=9 a:t_nodes=35 mismatches=0 forbidden=0 → OK
- readme-swiss: slides=8 a:t_nodes=31 mismatches=0 forbidden=0 → OK
- readme-expressive: slides=9 a:t_nodes=34 mismatches=0 forbidden=0 → OK
- readme-dense-technical: slides=10 a:t_nodes=39 mismatches=0 forbidden=0 → OK

The engine validator (`validatePptx`: 16:9, in-bounds rect-only shapes,
editable char count) also returned OK for all four at generation time.

## How the PNGs were rendered

The PNGs are rasterizations of the **real PPTX bytes** via macOS QuickLook
(`qlmanage -t -s 1280`), which renders slide 1 of a file. For the dense deck's
slide 2, a single-slide extract was produced by mechanical slide deletion only
(python-pptx, all other slides dropped) — zero edits to geometry, text, fonts,
or colors. Font faces fall back per the renderer where design faces are absent.

Why not browser previews: PNGs rendered from deck JSON through the Studio
SlideView HTML mapping clipped title descenders under browser font metrics
(the engine sizes boxes for PowerPoint metrics). Those clipped previews were
discarded; only real-PPTX renders are shipped. No pixel-parity claim against
Microsoft PowerPoint itself is made — these are QuickLook renders of genuine
engine PPTX output.
